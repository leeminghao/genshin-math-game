# AI 键盘和鼠标产品方案可行性报告

日期：2026-06-24  
状态：Pre-PRD 可行性评估，不建议直接进入完整 PRD 或硬件量产  

## 1. 结论摘要

本报告评估的产品方向是：

> 在 AI 键盘和鼠标中集成 AI 能力，将用户意图转换成物理键盘和鼠标事件，让电脑无法区分背后是人在操作还是人工智能在操作。

综合判断：

| 维度 | 判断 | 说明 |
|---|---|---|
| 技术可行性 | 中高 | 将意图转成键盘/鼠标/HID 事件可实现，市场上已有 RPA、宏键盘、AI GUI agent、AI 快捷键等相邻形态 |
| 用户价值 | 未验证 | 真实刚需不是“电脑无法区分”，而可能是跨软件自动化、旧系统操作、无障碍输入、重复办公提效 |
| 商业可行性 | 中低到中 | 若定位为合规、可审计的 AI 输入协助设备，有探索价值；若定位为隐蔽代操，商业和合规风险极高 |
| 合规/信任风险 | 极高 | “无法区分人和 AI”容易被用于规避平台检测、考试、游戏反作弊、办公审计、风控和权限边界 |
| 推荐决策 | Prototype first | 先做受限原型和特约用户验证，不进入硬件量产 |

核心建议：

1. 不要把“让电脑无法区分人和 AI”作为产品卖点。
2. 应重定位为：**本地、可控、可审计、用户确认后执行的 AI 输入协助硬件/软件系统**。
3. 最优先验证场景不是通用个人电脑全自动代操，而是低风险、高频、可审计的垂直场景：旧系统数据录入、软件测试、无障碍输入、企业内部流程、演示/培训自动化。
4. 第一版不应先做完整硬件。应先做“桌面 Agent + 虚拟输入/开发板 HID + 审计回放”的技术与价值原型。

|---|---|---|

## 3. 市场已有产品形态分析

### 3.1 AI 入口键：Microsoft Copilot key

事实：

- Microsoft 在 2024 年宣布 Windows 11 PC 将出现新的 Copilot key。
- 该键的核心价值是降低用户调用 AI 助手的入口成本。
- 这类形态本质是“AI 入口硬件化”，不是 AI 自动操作电脑。

对本产品启示：

- AI 键盘/鼠标的硬件入口有市场趋势。
- 但大厂做的是“显式唤起 AI”，不是“隐藏 AI 操作身份”。
- 入口键本身价值有限，真正价值在后续 AI 工作流。

### 3.2 上下文 AI 插入键：Chromebook Quick Insert key

事实：

- Chromebook Plus 相关产品引入 Quick Insert key。
- 该键不是单纯打开聊天窗口，而是给用户提供写作辅助、最近链接、文件、emoji/GIF 等上下文插入能力。

对本产品启示：

- “按键 + 当前上下文 + 直接插入结果”比单纯“打开 AI”更接近用户工作流。
- AI 键鼠可以优先做上下文输入增强，而不是全自动代操。

### 3.3 AI 鼠标/键鼠软件入口：Logitech AI Prompt Builder

事实：

- Logitech 已把 AI Prompt Builder 和键鼠生态结合，并推出带 AI prompt button 的鼠标。
- 其方向是让用户更容易调用 ChatGPT/AI prompt，而不是替用户隐蔽完成整套电脑操作。

对本产品启示：

- AI 外设已经开始出现，但现有形态偏“快捷入口 + prompt workflow”。
- 如果本产品只做一个 AI 键或 AI 鼠标按钮，差异化不足。
- 差异化应来自“跨软件动作执行 + 安全审计 + 高可靠工作流”。

### 3.4 GUI Agent：OpenAI Operator / ChatGPT agent

事实：

- OpenAI 官方说明 Operator 可使用浏览器执行任务，通过截图理解界面，通过点击、打字、滚动交互。
- OpenAI 明确强调用户可随时接管；登录、支付、验证码等敏感场景需要用户接管或确认。
- Operator 被定位为 research preview，并承认有局限。

对本产品启示：

- “AI 使用人类界面”是行业确定方向。
- 安全、确认、可接管是头部厂商的基本设计原则。
- 本产品如果走物理键鼠事件，必须更重视安全，因为它可能跨出浏览器沙箱。

### 3.5 GUI Agent：Anthropic computer use

事实：

- Anthropic 官方说明 Claude computer use 可以看屏幕、移动光标、点击按钮、输入文本。
- Anthropic 同时明确称该能力仍实验性、笨拙、容易出错；并建议从低风险任务开始。
- Anthropic 还指出 computer use 可能带来垃圾信息、错误信息、欺诈等新风险。

对本产品启示：

- 当前技术还没有达到“可靠替代人类全电脑操作”的成熟度。
- 不能承诺泛化自动完成复杂桌面任务。
- 产品必须从低风险、可回滚、可确认的任务开始。

### 3.6 桌面 RPA：Power Automate Desktop flows

事实：

- Microsoft Power Automate Desktop flows 能自动化重复桌面流程。
- 官方说明它可与现代应用、旧应用、Excel、文件夹、Web、UI 元素、图片或坐标交互。

对本产品启示：

- “自动化桌面流程”已有成熟替代方案。
- 本产品必须证明比 RPA 更易用、更跨环境、更低部署成本，或能处理 RPA 不适合的场景。

### 3.7 宏键盘/脚本工具：Stream Deck、AutoHotkey 等

事实：

- 市场已有可编程按键、宏脚本、热键和鼠标键盘自动化工具。
- 它们能将用户预定义动作映射成快捷键、宏、应用操作或脚本。

对本产品启示：

- “按一下触发动作”不构成差异化。
- 真正机会在于：用户不用写脚本，AI 能把意图转成可审计、可确认、可复用的动作计划。

## 4. 产品机会重新定义

### 4.1 原始方向

```text
AI 键盘/鼠标中集成 AI 能力
-> 用户表达意图
-> AI 转换为物理键盘和鼠标事件
-> 电脑无法区分是人还是 AI 操作
```

### 4.2 Y 模型转化

| 项 | 分析 |
|---|---|
| 表层请求 | AI 直接变成键盘鼠标操作，电脑无法区分人和 AI |
| 真实场景 | 用户想让 AI 操作任意软件，而不是受限于浏览器、API、插件、RPA 配置 |
| 底层需求 | 跨软件自动化、减少重复劳动、操作旧系统、降低脚本/RPA 使用门槛 |
| 坏结果规避 | 用户不想自己点击、复制、粘贴、填表、切窗口、重复录入 |
| 产品原则 | 用户授权、可见、可暂停、可撤销、可审计、低风险任务优先 |
| 推荐方案 | AI 输入协助设备/系统，不是隐蔽代操设备 |

### 4.3 推荐产品定义

> 面向需要跨软件重复操作的办公、测试、运维和无障碍用户，AI 输入协助设备将自然语言意图转成可预览、可确认、可审计的键盘鼠标动作计划，并通过标准输入事件执行，从而降低脚本和 RPA 门槛。

不推荐的定义：

> 让 AI 像真人一样隐蔽控制电脑，软件无法识别背后是否为 AI。

原因：

- 该定义把合规风险当作产品卖点。
- 容易吸引灰色用户和滥用场景。
- 企业客户、平台合作、支付渠道、应用商店、品牌传播都会受阻。

## 5. 目标用户和场景评估

### 5.1 候选用户优先级

| 用户 | 场景 | 需求强度 | 风险 | 推荐优先级 |
|---|---|---:|---:|---:|
| 企业旧系统操作人员 | ERP、CRM、财务系统、内网系统重复录入 | 高 | 中 | P0 |
| 软件测试/QA | 跨应用 UI 回归测试、演示数据录入 | 高 | 低中 | P0 |
| 无障碍/行动不便用户 | 用语言或少量按键完成复杂输入 | 高 | 中 | P0/P1 |
| 高级个人效率用户 | 邮件、表格、浏览器、文档重复操作 | 中 | 中 | P1 |
| 内容创作者/直播用户 | 控制软件、切场景、生成文本、执行宏 | 中 | 低 | P1 |
| 游戏/抢票/刷量/考试用户 | 绕过限制、批量点击、模拟真人行为 | 高 | 极高 | 明确不做 |

### 5.2 最值得验证的首场景

首选场景：**企业旧系统和表格/网页之间的数据迁移**

理由：

- 痛点高频、重复、可观察。
- 用户当前替代方案常是人工复制粘贴、RPA、脚本或外包录入。
- 标准 API 不一定可用，物理输入兼容性有价值。
- 可设置企业审计、白名单应用、操作日志。

示例任务：

```text
用户说：把这张 Excel 中未录入的 20 条客户信息填到内网页面。
AI：识别字段映射 -> 生成动作计划 -> 用户确认 -> 执行键鼠输入 -> 每条记录后写日志 -> 出错暂停等待用户处理。
```

## 6. 可行性评估

### 6.1 技术可行性

| 模块 | 可行性 | 说明 |
|---|---|---|
| 意图理解 | 中高 | LLM 可将自然语言转成步骤，但需限制任务范围 |
| 屏幕理解 | 中 | OCR/视觉模型可用，但复杂桌面 UI 准确率仍有限 |
| 动作规划 | 中 | 可转成点击、输入、快捷键、等待、检查等动作 |
| 物理输入执行 | 高 | USB HID、虚拟 HID、系统辅助功能接口、RPA 都可实现 |
| 错误检测 | 中低 | 需要截图比对、状态检查、日志、人工接管 |
| 安全控制 | 中 | 可设计确认、权限、白名单、暂停、审计，但会降低“全自动”吸引力 |
| 跨平台 | 中低 | Windows/macOS/Linux 权限模型、辅助功能授权、HID 行为差异明显 |

技术结论：

- “能做”不是问题。
- 难点是“可靠、安全、可解释、可商业化地做”。
- 物理 HID 是兼容性方案，不应成为绕过检测方案。

### 6.2 用户价值可行性

| 假设 | 当前判断 |
|---|---|
| 用户想让 AI 操作任意软件 | 有可能成立，但需场景验证 |
| 用户愿意购买新硬件而不是使用软件 Agent | 未证明 |
| 物理键鼠事件比软件自动化更有价值 | 仅在无 API、旧系统、权限受限、跨设备场景中可能成立 |
| 用户接受 AI 自动点击自己的电脑 | 需要强信任、透明和可撤销机制 |

用户价值结论：

- 用户真正需要的可能是“跨软件完成任务”，不是“电脑无法区分”。
- 若不能找到高频刚需场景，产品会变成酷炫外设而非刚需工具。

### 6.3 商业可行性

| 商业路径 | 可行性 | 说明 |
|---|---|---|
| 个人效率硬件 | 中低 | 市场大但付费弱，容易被系统级 AI 和软件 Agent 吞掉 |
| 企业流程自动化设备 | 中 | 客单价高，但销售周期、合规、IT 管理要求高 |
| QA/测试硬件 | 中高 | 场景清晰，风险较低，愿意为稳定性付费 |
| 无障碍辅助设备 | 中 | 用户价值强，但渠道、服务、合规和价格敏感 |
| 灰色自动化工具 | 短期高、长期低 | 容易吸引用户，但支付、渠道、法律和品牌风险极高 |

商业结论：

- 最稳路径不是 C 端通用外设，而是 B 端或专业场景。
- 建议先从 QA/旧系统/RPA 替代场景验证，避免泛化。

### 6.4 合规与安全可行性

高风险场景：

- 考试、招聘测评、游戏、抢票、刷量、社交平台批量行为。
- 银行、支付、证券、医疗、政务等高风险操作。
- 绕过软件自动化检测、验证码、反作弊、权限审计。

必须内置的限制：

1. 敏感动作用户确认。
2. 密码、支付、验证码、人脸、银行等场景默认接管。
3. 企业版本提供日志、回放、权限、白名单和审计。
4. 明确禁止规避检测和违反平台规则。
5. 默认暂停而不是默认强行继续。

## 7. 产品原则

1. **透明优先于隐蔽。** 产品必须让用户知道 AI 准备做什么、正在做什么、做完了什么。
2. **用户控制优先于自动化深度。** 用户可随时暂停、接管、撤销。
3. **兼容性优先于规避性。** 使用 HID 是为兼容旧系统，不是为绕过风控。
4. **低风险任务优先。** 首版只做可回滚、可审计、低损失任务。
5. **先垂直场景，后通用电脑控制。** 不做泛化承诺。
6. **动作计划必须可读。** AI 不能直接执行不可解释的动作序列。
7. **审计是基础功能，不是企业版附加项。**

## 8. MVP 建议

### 8.1 MVP 目标

验证核心假设：

> 在受限、低风险、重复的跨软件场景中，用户愿意让 AI 生成可确认的键鼠动作计划，并认为它比手工操作、宏工具或传统 RPA 更省事。

### 8.2 MVP 不建议做

| 不做 | 原因 |
|---|---|
| 不做量产键盘/鼠标 | 价值未验证，硬件周期和库存风险高 |
| 不做全电脑自动化 | 风险和失败率过高 |
| 不做隐蔽运行 | 合规和信任风险不可接受 |
| 不做高风险站点 | 支付、金融、考试、游戏等先排除 |
| 不做“真人模拟”卖点 | 容易吸引错误用户和监管风险 |

### 8.3 MVP 形态

建议做三件套：

1. **桌面 Agent 原型**
   - 接收自然语言任务。
   - 读取屏幕截图和当前窗口信息。
   - 生成动作计划。
   - 展示给用户确认。

2. **输入执行层**
   - 第一阶段可用软件虚拟输入或系统辅助功能 API。
   - 第二阶段用开发板模拟 USB HID。
   - 不急于做量产键盘/鼠标。

3. **审计和接管层**
   - 每一步记录：截图、动作、目标、结果。
   - 失败自动暂停。
   - 用户可随时接管。

### 8.4 MVP 场景

| 场景 | 任务 | 成功标准 |
|---|---|---|
| 表格到网页录入 | 从 Excel 复制 20 条记录到测试网页表单 | 90% 字段正确，出错可暂停修正 |
| 旧系统重复操作 | 在内部测试系统中完成固定流程 | 相比手工节省 50% 时间 |
| QA 回归演示 | 按指定步骤操作应用并记录结果 | 可重复运行 10 次且日志完整 |

### 8.5 MVP 验证指标

| 指标 | Go 阈值 | No-Go 含义 |
|---|---:|---|
| 任务成功率 | >= 80% | 技术可靠性不足，先不做硬件 |
| 用户确认后执行率 | >= 70% | 用户不信任动作计划 |
| 相比人工节省时间 | >= 40% | 价值不足 |
| 用户愿意继续使用 | 5/8 特约用户连续用 1 周 | 高频场景不成立 |
| 付费意愿 | 3/8 愿意为原型付费或签试点 | 商业需求弱 |
| 高风险请求占比 | < 20% | 定位吸引了错误用户 |

## 9. 风险清单

| 风险 | 严重度 | 说明 | 缓解动作 |
|---|---:|---|---|
| 灰色用途吸引 | 极高 | “无法区分人和 AI”会吸引作弊/刷量/规避检测 | 改定位，明确禁用场景，内置限制 |
| 任务失败损失 | 高 | AI 点错、输入错、提交错可能造成损失 | 计划预览、确认、暂停、回滚、白名单 |
| 用户不信任 | 高 | 用户不敢让 AI 操作电脑 | 透明日志、逐步授权、低风险任务起步 |
| 被系统级 AI 替代 | 高 | Windows/macOS/ChromeOS 可能直接内置 Agent | 选择旧系统、跨设备、企业审计、专业场景 |
| 硬件成本和库存 | 中高 | 量产硬件风险大 | 软件和开发板先验证 |
| 跨平台碎片化 | 中高 | 权限、输入、窗口、坐标差异 | 先只支持 Windows 或单一环境 |
| 商业采购阻力 | 中 | 企业 IT 和安全审批复杂 | 提供本地部署、日志、权限、数据边界 |

## 10. Go / No-Go 判断

### 当前建议

**Prototype first。不要直接写完整 PRD，不要立刻做硬件量产。**

### Go 条件

满足以下条件后再进入 PRD：

1. 明确一个 P0 目标用户：例如企业旧系统录入员、QA 测试人员、无障碍用户。
2. 找到一个高频、低风险、可审计任务。
3. 8 名特约用户完成 1 周试用。
4. 任务成功率 >= 80%。
5. 至少 3 名用户愿意付费或签试点。
6. 高风险/灰色用途请求占比可控。

### No-Go 条件

出现以下情况应暂停或转向：

1. 用户主要被“隐蔽代操”吸引。
2. 原型必须静默运行才有价值。
3. 用户不愿查看或确认动作计划。
4. 任务成功率长期低于 60%。
5. 主要场景集中在考试、游戏、刷量、抢票、绕过风控。

## 11. 推荐下一步

### 11.1 一周内完成

1. 访谈 10 个候选用户：
   - 3 个企业录入/运营人员。
   - 3 个 QA/测试人员。
   - 2 个高级效率用户。
   - 2 个无障碍/辅助输入相关用户或专家。

2. 每个访谈只问真实任务：
   - 过去一周最重复的电脑操作是什么？
   - 当前怎么解决？
   - 一次要花多久？
   - 出错代价是什么？
   - 愿不愿让 AI 代做？必须看到什么才敢用？

3. 输出场景优先级：
   - 频率。
   - 痛感。
   - 可自动化程度。
   - 出错损失。
   - 付费意愿。

### 11.2 两周内完成

做一个 Wizard-of-Oz / 半自动原型：

- 用户输入任务。
- 系统生成动作计划。
- 人工或半自动执行。
- 记录用户是否信任、是否确认、是否觉得省时间。

### 11.3 四周内完成

做技术 Spike：

- Windows 单平台。
- 单一测试网页或测试旧系统。
- 屏幕识别 + 动作计划 + 用户确认 + 输入执行 + 日志。
- 可选开发板 HID 执行。

## 12. 最终判断

这个方向有真实技术趋势支撑：AI 快捷键、上下文 AI 插入、GUI Agent、RPA、宏键盘和桌面自动化都在证明“AI + 人机输入界面”正在发生。

但原始表述中最危险的是：

> 让电脑无法区分背后是人在操作还是人工智能在操作。

这句话不应作为产品定位。它最多可以作为“底层兼容能力”的技术描述，不能作为市场卖点或产品原则。

更可行的产品方向是：

> AI 输入协助系统：在用户授权、确认和审计下，把自然语言意图转换为跨软件键鼠操作，帮助用户完成重复、低风险、可验证的电脑任务。

建议当前决策：

**继续探索，但先做 Pre-PRD 原型验证；只有当垂直场景和付费意愿被证明后，再写完整 PRD 并考虑硬件化。**
